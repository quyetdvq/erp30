# Contact — Module Design Record (Backend Rewrite)

- **Owner:** `Contact`, exactly one root. Corresponds to Contact in System Architecture Standard v1.1.1; never `ContactsManagement` or a writable `Contact` submodule under Organization/People.
- **Tables:** `contacts` (write). Trusted owner facts are read-only via Organization persistence and `AccessReadAdapters::people()` (PeopleFactsPort); no writes to People or Organization tables.
- **Owner invariant:** `contact_type` and `contact_ref_id` are immutable. Supported owners: `ORGANIZATION`, `EMPLOYEE` (P1), `CUSTOMER` (P2-CUS), `SUPPLIER` (P2-SUP-T06 backend source). PBAC resources respectively: `organization_contact`, `employee_contact`, `customer_contact`, `supplier_contact`. Legacy `contact` is not an authorization resource. Organization scope derives only from persisted Organization or unique effective primary Employee Assignment; Customer/Supplier scopes are GROUP MASTER with independent parent VIEW. No request-supplied scope.
- **HTTP:** ContactController owns two GET and three mutations; frozen P1 routes and API-010 operations are unchanged. GET list/detail compile four-owner SQL-first scopes under one REPEATABLE READ snapshot before COUNT/search/sort/LIMIT; every returned row is canonical VIEW-checked without post-filtering. POST/PATCH require an authenticated actor and existing DEV write gate. PATCH/SetState also enforce persisted Contact VIEW, parent VIEW where applicable, PBAC and owner immutability. OpenAPI/FE Supplier owner work remains gated by SUP MOD-G2.
- **State:** initial status from configured Lifecycle for selected resource; PATCH cannot change status. POST set-state checks one approved `setstate` transition and PBAC including the actual transition action.
- **Transaction:** mutation service owns Contact writes, row locking on PATCH/set-state, created_by/updated_by from authenticated actor, rollback on failure.
- **Locales:** stable `CONTACT_*` codes map through baseline en/vi Contact dictionaries. No exception trace exposed to API responses.
- **SQL authorization:** Organization owner must exist. Employee owner must exist with exactly one UTC-effective ACTIVE primary assignment and an existing Organization. Customer/Supplier owners must have persisted parents and satisfy BOTH Contact-resource VIEW and parent-resource VIEW. Supplier parent additionally needs its persisted `group_organization_id` to equal the trusted GROUP root. COUNT/page/detail use identical canonical SQL predicates and the M8.7 audit mirrors all six underlying scopes. Supplier parent rows are loaded once per result page (batch, no per-Contact Supplier lookup). `contacts.*` only, no synthetic organization_id in API data. Scope enumeration is bounded and fail-closed.
- **Limitations:** P2-SUP-T06 implementation is **backend source/offline only**, not DEV UAT or release. Supplier catalog/Lifecycle must be provisioned on an approved DEV clone before exercising Contact runtime; T00 Security/DBA and migration gates remain blocked. MOD-G2 OpenAPI/typed FE Supplier Contact coverage and operator review of PC-06 are still pending. Live MariaDB PBAC parity, Unicode/NULL/sort, EXPLAIN/HTTP, concurrent owner/assignment changes and browser tests remain unverified. Frozen route and P1 contracts must remain intact.
